Developing XH Modules

Human/Vertebrate Host Infection Dynamics

This vignette discusses how to add a new XH module to ramp.library. As background, we strongly recommend reading the ramp.xds vignette about the XH Interface.

Each XH module implements a unique model family describing human/host infection dynamics and immunity that can be used by ramp.xds. Before writing a new module, please check and see if the model family is already part of the SimBA library.

If you need help, please contact Professor David L Smith

We have written this vignette to produce a new template file using knitr::purl. The template can be modified to build a new XH module.

Do this:

  1. Download the markdown file that created this document “X-How_To_Add_Model.Rmd.”

  2. Set your working directory to the location of the downloaded copy of “X-How_To_Add_Model.Rmd”

  3. Execute these commands:

library(knitr)
knitr::purl("X-How_To_Add_Model.Rmd", 
            output = "XHmodule-newXHname.R", 
            documentation = 0, 
            quiet=TRUE)

  1. You should see a new file called XHmodule-newXHname.R in the working directory. You can now move and rename it.

  2. Open the file and do a global search for newXHname and replace it with a short string that will define the model as its XHname.

  3. Edit the functions following the directions below.

Style Guide

We recommend that new models conform to a set of style guidelines:

  • Retrieve state variables by name using the indices attached to XH_obj.

  • All documentation is written in roxygen2

  • Functions should use with(*,{...}) to make the code easier to read.

  • A vignette should accompany each model, including citations to the relevant publications, and proposed tests of the code.

  • The functions should be easy to relate to the equations defining a model, following notation defined in an accompanying vignette.

Documentation policy

Follow the shared function order in module files and guide implementation sections. Move functions with their documentation, keep file-level review/TODO notes at the top, and preserve definitions and behavior when reordering.

Follow the shared documentation conventions for all component modules. These vignettes are the public style reference; keep template documentation aligned with the implemented functions.

  • Use the approved family titles, with the module name in backticks and the XH component tag.
  • Describe the function’s behavior, not just which generic it implements. Show the actual derivative or updating equations, in returned-vector order, including demographic, treatment, and accessory terms when used.
  • Put storage locations, class assignments, and dispatch mechanics in @note. Explain generic dispatch on the generic, not on every method.
  • Describe setup with an ordered-by-implementation bulleted list covering the constructor and dimension, initial values, and each interface call. End every complete bullet with a period.
  • Each S3 method uses @inheritParams from its immediate generic, even when that generic inherits its argument documentation. Document method-specific arguments or restrictions locally with @param.
  • Qualify links to shared helpers with ramp.xds::. Setup and check methods return “an xds model object”.
  • Describe skill sets as capabilities and compatibilities. Include dts = FALSE if there is no discrete-time update method; advertise discrete-time support only when it is implemented and tested.
  • State explicitly when a check method performs no checks.

The template includes both dynamics alternatives for illustration. Retain the methods appropriate to the new module, replace all placeholder equations, and make the skill set match the supported solver pathways.

Dynamics

dXHdt

The sections that need to be modified are marked # Change this

  • Replace X1 with the name of your first state variable, and replace F_1 with the formula that computes its derivative. Do the same with X2 and add lines for each state variable.

  • The method reads the stored FoI from xds_obj$terms$FoI[[i]]. Use the shared Births(t, y, xds_obj, i) and Deaths functions for demographic terms, as shown below. Return derivatives in the same order as the indexed state variables.

#' @title Compute the derivatives for `newXHname` (**XH**)
#' @description For the `newXHname` differential equation system:
#' \deqn{\frac{dH}{dt} = \mathrm{Births}(t,y) - \mathrm{Deaths}(t,H)}
#' \deqn{\frac{dX_1}{dt} = F_1(\mathrm{foi},X_1,X_2) - \mathrm{Deaths}(t,X_1)}
#' \deqn{\frac{dX_2}{dt} = F_2(\mathrm{foi},X_1,X_2) - \mathrm{Deaths}(t,X_2)}
#' Replace the placeholder functions and these equations together.
#' @inheritParams ramp.xds::dXHdt
#' @return a [numeric] vector
#' @export
dXHdt.newXHname <- function(t, y, xds_obj, i) {

  # do not change this
  foi <- xds_obj$terms$FoI[[i]]

  # do not change this
  # attach the variables by name 
  with(get_XH_vars(y, xds_obj, i),{
    # do not change this
    # attach the parameters by name 
    with(xds_obj$XH_obj[[i]], {
      # Do not change this 
      dH <- Births(t, y, xds_obj, i) - Deaths(t, H, xds_obj, i)
      # Change this
      dX1 <- F_1(foi, X1, X2) - Deaths(t, X1, xds_obj, i)
      dX2 <- F_2(foi, X1, X2) - Deaths(t, X2, xds_obj, i)
      
      # Change this 
      derivs <- c(dH, dX1, dX2)
      
      # return the derivatives 
      return(derivs)
    })
  })
}

Update_XHt (discrete-time modules)

This is the discrete-time alternative to dXHdt. The SIS module provides both dXHdt.SIS and Update_XHt.SIS as examples of the two solver pathways.

#' @title Update states for `newXHname` (**XH**)
#' @description For the `newXHname` discrete-time system, the updating function is:
#' \deqn{H_{t+1} = H_t}
#' \deqn{X_{1,t+1} = X_{1,t} + F_1(\mathrm{ar},X_{1,t},X_{2,t})}
#' \deqn{X_{2,t+1} = X_{2,t} + F_2(\mathrm{ar},X_{1,t},X_{2,t})}
#' Replace the placeholder functions and these equations together.
#' @inheritParams ramp.xds::Update_XHt
#' @return a [numeric] vector
#' @export
Update_XHt.newXHname <- function(t, y, xds_obj, i) {
  ar <- xds_obj$terms$AR[[i]]

  # do not change this
  # attach the variables by name 
  with(get_XH_vars(y, xds_obj, i),{
    # do not change this
    # attach the parameters by name 
    with(xds_obj$XH_obj[[i]], {
      # For a static-population example; add demographic updates if needed.
      Ht <- H
      # Change this. Use ar for infection events in a discrete-time model.
      X1t <- X1 + F_1(ar, X1, X2)
      X2t <- X2 + F_2(ar, X1, X2)
      
      # Change this 
      states <- c(Ht, X1t, X2t)
      
      # return the updated state variables
      return(states)
    })
  })
}

State-variable extraction

This method primarily supports solver evaluations that need variables by name; users rarely call it directly. Follow the title and description below, document any derived quantities, and put index storage in @note. Return a named list; do not confuse extraction from y with output parsing.

In the following, each variable in your model gets its own pair of lines.

  • Leave H as-is

  • Replace X1 in X1 and X1_ix with the first variable name.

  • Replace X2 in X2 and X2_ix with the second variable name.

  • Copy the form for every other variable

  • The variable X0 is the class that gets newborns. If you use it or if you want to have it available, compute it and add it to the returned list.

#' @title Get the state variables for `newXHname` (**XH**)
#' @description Extract the state variables for the `newXHname` module
#' from `y` and return them by name in a list for use during model solving.
#' Also compute the remaining class `X0 = H - X1 - X2`.
#' @note Variable indices are stored at `xds_obj$XH_obj[[i]]$ix`.
#' @inheritParams ramp.xds::get_XH_vars
#' @return a named [list] of state variables and module-specific derived quantities
#' @export
get_XH_vars.newXHname <- function(y, xds_obj, i) {
  with(xds_obj$XH_obj[[i]]$ix,{
      H = y[H_ix]
      X1 = y[X1_ix]
      X2 = y[X2_ix]
      X0 = H-X1-X2 
      return(list(H=H, X1=X1, X2=X2, X0=X0))})
}

XH Model Object

make_XH_obj

Use the title “Make a module object for module (XH)”. Describe the parameters initialized by the constructor and their relationship to the getter and changer. Each of these three functions links to the other two in @seealso; document any differences in supported parameters explicitly.

  • In the following, replace p1 with the first parameter, p2 with the second, and so on.

  • Shared demographic and mass-treatment features are initialized by setup_XH_obj using the ramp.xds setup functions; do not create a separate demographic matrix or replace these ports in make_XH_obj.

  • If the module supports mass drug administration or mass screen and treat, include the corresponding treatment terms in its state updates and record that capability in get_skillset_XH.newXHname.

#' @title Make a module object for `newXHname` (**XH**)
#' @description Create a `newXHname` module object and initialize its parameters.
#' Inspect parameters with [get_XH_pars.newXHname] and change supported values
#' with [change_XH_pars.newXHname]. Values in `options` override parameter arguments.
#' @seealso [get_XH_pars.newXHname], [change_XH_pars.newXHname]
#' @param nStrata is the number of population strata
#' @param options a [list] that could override defaults
#' @param p1 the first parameter 
#' @param p2 the second parameter 
#' @param p3 the third parameter 
#' @param q test positivity
#' @return a [list]
#' @export
make_XH_obj_newXHname = function(nStrata, options=list(),
                         p1=1, p2=2, p3=3, q=0.8){
  with(options,{
    XH_obj = list()
    class(XH_obj) <- c("newXHname")

    # Change this
    XH_obj$p1 = checkIt(p1, nStrata)
    XH_obj$p2 = checkIt(p2, nStrata)
    XH_obj$p3 = checkIt(p3, nStrata)
    XH_obj$q = checkIt(q, nStrata)

    return(XH_obj)
  })}

setup_XH_obj

This method also initializes the shared XH interface features. Follow the setup sequence used by existing modules.

#' @title Set up the module object for `newXHname` (**XH**)
#' @description Set up a `newXHname` module object for the **XH** component
#' and the \eqn{i^{th}} host species.
#' + Set the module name to `newXHname`.
#' + Create the module object with [make_XH_obj_newXHname], passing `nStrata[i]` and `options`.
#' + Set initial values using [ramp.xds::setup_XH_inits], passing `options` to override defaults.
#' + Initialize blood search weights using [ramp.xds::setup_blood_search_weights.setup].
#' + Initialize the time-spent matrix using [ramp.xds::setup_timespent.setup].
#' + Initialize mass-treatment functions using [ramp.xds::setup_mass_treatment].
#' + Initialize birth and death rates using [ramp.xds::setup_demog_obj].
#' + Initialize time away using [ramp.xds::setup_time_away.setup].
#' + Initialize travel EIR using [ramp.xds::setup_travel_eir.no_travel].
#' + Return the updated **`xds`** model object.
#' @note The module object is stored at `xds_obj$XH_obj[[i]]`.
#' @inheritParams ramp.xds::setup_XH_obj
#' @return an **`xds`** model object
#' @export
setup_XH_obj.newXHname = function(XHname, residence, xds_obj, options=list(), i=1){
  xds_obj$XHname = "newXHname"
  xds_obj$XH_obj[[i]] = make_XH_obj_newXHname(xds_obj$nStrata[i], options)
  xds_obj <- setup_XH_inits(xds_obj, options=options, i=i)
  xds_obj <- setup_blood_search_weights("setup", xds_obj, i=i)
  xds_obj <- setup_timespent("setup", xds_obj, list(residence=residence), i)
  xds_obj <- setup_mass_treatment(xds_obj, i=i)
  xds_obj <- setup_demog_obj(xds_obj, i)
  xds_obj <- setup_time_away("setup", xds_obj, i=i)
  xds_obj <- setup_travel_eir("no_travel", xds_obj, i=i)
  return(xds_obj)
}

Parameters

Implement methods to inspect and change the module’s parameters. The options argument is a named list; parameters not supplied in options retain their existing values when changed.

#' @title Get parameters for `newXHname` (**XH**)
#' @description Return the parameters for the `newXHname` module as a named list.

#' @inheritParams ramp.xds::get_XH_pars
#' @return a named [list] of parameter values
#' @export
get_XH_pars.newXHname <- function(xds_obj, i=1) {
  with(xds_obj$XH_obj[[i]], list(p1=p1, p2=p2, p3=p3, q=q))
}

#' @title Change parameters for `newXHname` (**XH**)
#' @description Change parameter values named in `options` for the `newXHname`
#' module, leaving other values unchanged.
#' @seealso [make_XH_obj_newXHname], [get_XH_pars.newXHname]
#' @inheritParams ramp.xds::change_XH_pars
#' @return an **`xds`** model object
#' @export
change_XH_pars.newXHname <- function(xds_obj, options=list(), i=1) {
  with(xds_obj$XH_obj[[i]], with(options, {
    if (!is.null(p1)) xds_obj$XH_obj[[i]]$p1 <- p1
    if (!is.null(p2)) xds_obj$XH_obj[[i]]$p2 <- p2
    if (!is.null(p3)) xds_obj$XH_obj[[i]]$p3 <- p3
    xds_obj$XH_obj[[i]]$q <- q
    xds_obj
  }))
}

Getter documentation uses “Get initial values (XH)”, describes returning stored values, puts storage in @note, and links to setup/change functions.

Initial-value constructors use the title “Make initial values for module (XH)” and return “a named [list] of initial values”. Describe creation and options overrides as in the example below, preserving any model-specific explanation. The constructor, setup method, and change method each link to the other two in @seealso.

Document numeric scalar expansion to nStrata and the required length for non-scalar initial values. State additional input restrictions and any internally constructed accessory values. For example, garki requires positive H; SEISd initializes cases to zero and SIPd initializes cfoi to zero rather than accepting independent overrides for those fields.

make_XH_inits

#' @title Make initial values for `newXHname` (**XH**)
#' @description Create a named list of initial values for the `newXHname` module.
#' Values in `options` override the defaults.
#' @details Initial values must be numeric scalars or have length `nStrata`.
#' Scalars are expanded to that length.
#' @param nStrata the number of strata in the model
#' @param options a [list] to override defaults
#' @param X1 the initial value for X1 
#' @param X2 the initial value for X2
#' @return a named [list] of initial values
#' @seealso [setup_XH_inits.newXHname], [change_XH_inits.newXHname]
#' @export
make_XH_inits_newXHname = function(nStrata, options = list(), H=1000, X1=1, X2=1){with(options,{
  H = unname(as.vector(checkIt(H, nStrata)))
  X1 = unname(as.vector(checkIt(X1, nStrata)))
  X2 = unname(as.vector(checkIt(X2, nStrata)))
  return(list(H=H, X1=X1, X2=X2))
})}

Variable indices

setup_XH_ix

Retrieve stored indices with the shared ramp.xds::get_XH_ix(xds_obj, i = 1); do not implement a module-specific getter. It returns the ix field directly: a named list of variable indices, an empty list if stored, or NULL if absent. Getter documentation uses “Get variable indices (XH)”, describes returning stored indices for the selected host species, puts storage in @note, and links to setup_XH_ix.

Use the title and description below, documenting allocation order and block lengths. Put index storage and the updated maximum in @note; the method returns the model object, not the index list. Record actual legacy storage exceptions separately rather than copying them into new models.

In the following, each variable in your model gets its own pair of lines. Replace X1 in X1_ix with the first variable name, X2 in X2_ix with the second, and add lines for each variable by copying and pasting and editing the pair of lines. Be sure the replacement gets applied to all four instances.

#' @title Set up variable indices for `newXHname` (**XH**)
#' @description Assign consecutive variable indices for the `newXHname` module,
#' starting after `xds_obj$max_ix`, and update the maximum index.
#' Allocate blocks in the order `H_ix`, `X1_ix`, `X2_ix`.
#' Each block has length `nStrata[i]`.
#' @note Indices are stored at `xds_obj$XH_obj[[i]]$ix`.
#' The maximum index is stored at `xds_obj$max_ix`.
#' @inheritParams ramp.xds::setup_XH_ix
#' @return an **`xds`** model object
#' @importFrom utils tail
#' @export
setup_XH_ix.newXHname <- function(xds_obj, i) {with(xds_obj,{

  H_ix <- seq(from = max_ix+1, length.out=xds_obj$nStrata[i])
  max_ix <- tail(H_ix, 1)
  
  X1_ix <- seq(from = max_ix+1, length.out=xds_obj$nStrata[i])
  max_ix <- tail(X1_ix, 1)

  X2_ix <- seq(from = max_ix+1, length.out=xds_obj$nStrata[i])
  max_ix <- tail(X2_ix, 1)
  
  xds_obj$max_ix = max_ix
  xds_obj$XH_obj[[i]]$ix = list(H_ix=H_ix, X1_ix=X1_ix, X2_ix=X2_ix)
  return(xds_obj)
})}

#' @title Parse outputs for `newXHname` (**XH**)
#' @description Extract the model state outputs for the `newXHname` module
#' from `outputs` and return them by name in a list.
#' Also compute `X0 = H-X1-X2`.
#' @note Variable indices are stored at `xds_obj$XH_obj[[i]]$ix`.
#' @inheritParams ramp.xds::parse_XH_orbits
#' @return a [list]
#' @export
parse_XH_orbits.newXHname <- function(outputs, xds_obj, i) {
  with(xds_obj$XH_obj[[i]]$ix,{
    H <- outputs[,H_ix]
    X1 <- outputs[,X1_ix]
    X2 <- outputs[,X2_ix]
    X0 <- H-X1-X2
    vars <- list(H=H, X1=X1, X2=X2, X0=X0)
    return(vars)
})}

Observed prevalence

All current XH modules except hMoI have a test-positivity parameter q, defaulting to 0.8, and compute observed prevalence as q times their true prevalence. The trivial module returns an empty numeric vector. Retain any diagnostic-specific parameters and methods when adding this observation model.

The hMoI module instead computes observed prevalence as 1 - exp(-m2), without q. Its three diagnostic methods are compatibility aliases for F_pr_obs, and its skill set reports pr_obs = TRUE with all three pf_* flags set to FALSE.

#' @title Compute observed prevalence
#' @description Return test positivity times true prevalence.
#' @inheritParams ramp.xds::F_pr_obs
#' @return a [numeric] vector of length `nStrata`
#' @export
F_pr_obs.newXHname <- function(vars, XH_obj) {
  XH_obj$q * ramp.xds::F_prevalence(vars, XH_obj)
}

Diagnostic prevalence

The SIS module uses a single test-positivity parameter q (default 0.8). Its F_pr_obs.SIS method computes q * I / H, and its three F_pfpr_by_* methods are compatibility aliases for that calculation, not distinct diagnostic models. Its skill set has pr_obs = TRUE and all three pf_* flags set to FALSE. Use get_PR(xds_obj, method = "obs") after solving to retrieve observed prevalence.

Other modules can implement the methods relevant to their diagnostic outputs; replace X1/H and the diagnostic parameter names below with the appropriate formulas and parameters for the model. These diagnostic-specific examples do not describe the SIS parameterization.

#' @title Compute observed prevalence by light microscopy
#' @inheritParams ramp.xds::F_pfpr_by_lm
#' @return a [numeric] vector of length `nStrata`
#' @export
F_pfpr_by_lm.newXHname <- function(vars, XH_obj) {
  with(vars, with(XH_obj, q_lm*X1/H))
}

#' @title Compute observed prevalence by RDT
#' @inheritParams ramp.xds::F_pfpr_by_rdt
#' @return a [numeric] vector of length `nStrata`
#' @export
F_pfpr_by_rdt.newXHname <- function(vars, XH_obj) {
  with(vars, with(XH_obj, q_rdt*X1/H))
}

#' @title Compute observed prevalence by PCR
#' @inheritParams ramp.xds::F_pfpr_by_pcr
#' @return a [numeric] vector of length `nStrata`
#' @export
F_pfpr_by_pcr.newXHname <- function(vars, XH_obj) {
  with(vars, with(XH_obj, q_pcr*X1/H))
}

  list(
    dts=FALSE,
    xde=TRUE,
    delay=FALSE,
    demography=TRUE,
    malaria=TRUE,

    pf_rdt=TRUE,

Use these logical fields for XH skill sets, choosing values for the module’s supported capabilities. Models with malaria = FALSE, including SIR, SIRS, SEIR, and SEIRV, omit all three pf_* fields. For a module supporting F_pr_obs, include pr_obs = TRUE after malaria. Compatibility aliases do not imply distinct diagnostic capabilities.

xds_plot_X.newXHname

#' Plot the density of infected individuals for the newXHname model
#'
#' @inheritParams ramp.xds::xds_plot_X
#' @export
xds_plot_X.newXHname = function(xds_obj, i=1, clrs=c("darkblue","darkred"), llty=1, add=FALSE){
  XH <- xds_obj$outputs$orbits$XH[[i]]
  time <- xds_obj$outputs$time
  if (add==FALSE)
    plot(time, 0*time, type="n", ylim=c(0, max(XH$H)),
         ylab="State density", xlab="Time")
  add_lines_X_newXHname(time, XH, xds_obj$nStrata[i], clrs, llty)
}

Module-specific line plotting function

add_lines_X_newXHname

#' Add lines for the `newXHname` state variables
#'
#' @param time simulation time points
#' @param XH a list with the outputs of parse_XH_orbits.newXHname
#' @param nStrata the number of population strata
#' @param clrs a vector of colors
#' @param llty an integer (or integers) to set the `lty` for plotting
#'
#' @export
add_lines_X_newXHname = function(time, XH, nStrata, clrs=c("darkblue","darkred"), llty=1){
  with(XH,{
    if(nStrata==1) {
      lines(time, X1, col=clrs[1], lty = llty[1])
      lines(time, X2, col=clrs[2], lty = llty[1])
    }
    if(nStrata>1){
      if (length(clrs)==2) clrs=matrix(clrs, 2, nStrata)
      if (length(llty)==1) llty=rep(llty, nStrata)

      for(i in 1:nStrata){
        lines(time, X1[,i], col=clrs[1,i], lty = llty[i])
        lines(time, X2[,i], col=clrs[2,i], lty = llty[i])
      }
    }
  })}

Reusable Code

ramp.xds has a modular design. The modular design makes it possible to break down published models to serve as dynamical components in new models for malaria, a kind of plug-and-play functionality for two kinds of systems:

  • systems of ordinary and delay differential equations models for malaria and other mosquito-transmitted pathogens.

  • stochastic and deterministic discrete time systems for malaria and other mosquito-transmitted pathogens.

This package – ramp.library – is a collection of models to implement a large number of dynamical model families and other algorithms taken from the literature describing malaria and other mosquito-transmitted pathogens (see Reiner, et al. 2013)1. Those models have been implemented here as code that has undergone rigorous testing and that can be used to build models for simulation-based analytics.

The mathematics supporting this framework were explained in Spatial Dynamics of Malaria Transmission 2
