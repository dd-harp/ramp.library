Developing MY Modules

Models for Adult Mosquito Ecology and Infection Dynamics

This vignette describes how to add an adult mosquito (MY) model module to ramp.library. Before creating a new module, check whether the model family is already available in the SimBA library. For an overview of the component interfaces, see the ramp.xds MY interface vignette.

An MY module represents adult mosquito ecology and, when applicable, pathogen infection dynamics in mosquitoes. It supplies methods that integrate with ramp.xds, which provides the shared model setup, transmission, egg-laying, and solver interfaces.

Create a module template

This vignette’s R code chunks can be extracted to create a starting R file. Download MY-How_To_Add_Model.Rmd, set your working directory to the folder containing it, then run:

knitr::purl(
  "MY-How_To_Add_Model.Rmd",
  output = "adult-MY-newMYname.R",
  documentation = 0,
  quiet = TRUE
)

Replace newMYname throughout the extracted file with a short, unique class name for the model. Review every placeholder and adapt the methods to the model’s equations and state variables before using the file.

Conventions

  • MY methods dispatch on the class of xds_obj$MY_obj[[s]]; use s as the vector-species index in method signatures and calls.
  • Use get_MY_vars(y, xds_obj, s) to retrieve named state variables, and keep the order of variables consistent across setup_MY_ix, get_MY_vars, initial values, and the dynamics.
  • Document the model’s state variables, parameters, equations, assumptions, and relevant references in roxygen.
  • Add tests for setup, parameter and initial-value changes, dynamics, and any model-specific outputs.

Documentation policy

Follow the shared function order in module files and guide implementation sections. Move functions with their documentation, keep file-level review/TODO notes at the top, and preserve definitions and behavior when reordering.

Follow the shared documentation conventions and the MY setup wording. These vignettes are the public style reference for both packages.

  • Use the approved family titles with the module name in backticks and the MY tag. Bionomics titles are “Mosquito bionomics for module (MY)”; effect-size titles are “Apply effect sizes for module (MY)”.
  • Describe the actual equations, including accessory derivatives and delayed branches. Replace placeholder descriptions with formulas when implementing the model; keep returned states and equations in the same order.
  • Keep storage, class assignments, and dispatch mechanics in @note. Describe generic dispatch on the generic rather than repeating it on methods.
  • List setup actions in code order, including the constructor with nPatches and options, skill set, initial values, and any shared ports. End with “Return the updated xds model object.”
  • Use method-specific helper links for circadian and dispersal initialization, qualified with ramp.xds::, and end complete bullets with periods. Only list interfaces the method actually sets up.
  • Describe skill sets as capabilities and compatibilities, and explicitly include dts = FALSE when no discrete-time update method is defined.
  • Document any checks actually performed. A no-op check returns the model unchanged; it does not validate the setup.

The minimal setup example below does not configure shared bionomics, circadian, or matrix ports. Add the helpers required by the implemented equations and document each call using the MY setup wording. Do not copy matrix-port configuration without checking the module’s needs.

State-variable extraction

get_MY_vars.newMYname maps the dependent-variable vector y to the named state variables used in the equations. Include only variables that belong to the module’s state vector; do not add host variables unless they are actual MY states.

#' @title Get the state variables for `newMYname` (**MY**)
#' @description Extract the state variables for the `newMYname` module
#' from `y` and return them by name in a list for use during model solving.
#' @note Variable indices are stored at `xds_obj$MY_obj[[s]]$ix`.
#' @inheritParams ramp.xds::get_MY_vars
#' @return a named [list] of state variables and module-specific derived quantities
#' @export
get_MY_vars.newMYname <- function(y, xds_obj, s) {
  with(xds_obj$MY_obj[[s]]$ix, {
    list(
      M = y[M_ix],
      Y = y[Y_ix]
    )
  })
}

Bionomics and effect sizes

For bionomic parameters managed through shared ports, implement MBionomics.newMYname to evaluate their baseline values at time t, and MEffectSizes.newMYname to apply the intervention effects. These methods receive t, y, xds_obj, and s, and return the updated xds_obj.

For each parameter x configured as a port, bionomics stores x_t and resets es_x to 1; effect sizes set x = x_t * es_x. Parameters without ports are stored directly as x and are not modified by effect sizes. This also applies to EIP (eip_t, es_eip) and the standard dispersal matrix (K_matrix_t, es_K_matrix). Matrix effects use elementwise * and must preserve the dispersal-matrix constraints. Recompute demographic and survival matrices using the realized parameters, and have dynamical parameter accessors such as get_f read those values without applying effects again. Document separately whether get_MY_pars reports baselines or realized values.

The SI module is an example of a module using the shared parameter helpers for feeding rate (f), human fraction (q), mortality (g), emigration (sigma), emigration loss (mu), oviposition rate (nu), and EIP duration. Use only the parameters relevant to the model.

Interface outputs

Implement the following methods with one value per patch:

  • F_fqZ.newMYname returns the daily density of infectious mosquito bites on humans (fqZ). The transmission interface uses it to compute EIR by human stratum.
  • F_fqM.newMYname returns the daily density of mosquito bites on humans (fqM). The transmission interface uses it to compute HBR by human stratum.
  • F_eggs.newMYname returns daily egg production by adult mosquitoes in each patch. The egg-laying interface distributes the eggs among habitats.

Each method receives t, y, xds_obj, and s.

For egg production, use “Compute egg production for module (MY)”. Use the description “Return the number of eggs laid by the adult mosquito population, per patch” and return “a [numeric] vector of length nPatches”. Inherit the module NULL anchor’s Egg Laying section using @inheritSection newMYname Egg Laying. In that section, explain which mosquitoes lay eggs: total adult density or, in behavioral-state models, gravid density. Multiply that density by the oviposition rate and eggs per batch. Link the method to its module and ramp.xds::EggLaying.

Mosquito-matrix accessors

Use the shared ramp.xds::get_Omega(xds_obj, s = 1) and ramp.xds::get_Upsilon(xds_obj, s = 1) to retrieve the stored mosquito demographic matrix, \(\Omega\), and EIP survival-and-dispersal matrix, \(\Upsilon\), respectively. Do not implement module-specific getter methods. They read xds_obj$MY_obj[[s]]$Omega and xds_obj$MY_obj[[s]]$Upsilon without recomputing matrices or modifying the model object. Each returns a matrix of dimensions nPatches by nPatches, or NULL if the corresponding matrix is not stored.

Their titles are “Get the mosquito demographic matrix (MY)” and “Get the EIP survival-and-dispersal matrix (MY)”. Document storage and the absence of recomputation in @note, and link to the other getter, the corresponding ramp.xds::change_Omega or ramp.xds::change_Upsilon function, and ramp.xds::xds_info_mosquito_demography.

make_MY_obj_newMYname creates the module-specific list and assigns its class. setup_MY_obj.newMYname attaches it to the full xds_obj. Parameters that use the shared bionomics or dispersal interfaces should be set up with the corresponding ramp.xds helpers.

#' @title Make a module object for `newMYname` (**MY**)
#' @description Create a `newMYname` module object and initialize its parameters.
#' Inspect parameters with [get_MY_pars.newMYname] and change supported values
#' with [change_MY_pars.newMYname]. Values in `options` override parameter arguments.
#' @seealso [get_MY_pars.newMYname], [change_MY_pars.newMYname]
#' @param nPatches number of patches
#' @param options named values that override defaults
#' @return a list
#' @export
make_MY_obj_newMYname <- function(nPatches, options = list(), p1 = 1) {
  with(options, {
    MY_obj <- list()
    MY_obj$p1 <- checkIt(p1, nPatches)
    MY_obj$nPatches <- nPatches
    class(MY_obj) <- "newMYname"
    MY_obj
  })
}

#' @title Set up the module object for `newMYname` (**MY**)
#' @description Set up a `newMYname` module object for the **MY** component
#' and the \eqn{s^{th}} vector species.
#' + Create the module object with [make_MY_obj_newMYname], passing `nPatches` and `options`.
#' + Set the skill set using [ramp.xds::get_skillset_MY].
#' + Set initial values using [ramp.xds::setup_MY_inits], passing `options` to override defaults.
#' + Return the updated **`xds`** model object.
#' @note The module object is stored at `xds_obj$MY_obj[[s]]`.
#' @inheritParams ramp.xds::setup_MY_obj
#' @return an **`xds`** model object
#' @export
setup_MY_obj.newMYname <- function(MYname, xds_obj, options = list(), s = 1) {
  xds_obj$MY_obj[[s]] <- make_MY_obj_newMYname(xds_obj$nPatches, options)
  xds_obj$MY_obj[[s]]$skill_set <- get_skillset_MY(xds_obj, s)
  xds_obj <- setup_MY_inits(xds_obj, options = options, s = s)
  xds_obj
}

#' @title Change parameters for `newMYname` (**MY**)
#' @description Change parameter values named in `options` for the `newMYname`
#' module, leaving other values unchanged.
#' This example supports changes to `p1`.
#' Call [ramp.xds::MBionomics] at time zero after changing parameters;
#' do not call [ramp.xds::MEffectSizes].

  xds_obj <- ramp.xds::MBionomics(0, y, xds_obj, s)
  xds_obj
}

#' @title Make initial values for `newMYname` (**MY**)
#' @description Create a named list of initial values for the `newMYname` module.

#' @details Initial values must be numeric scalars or have length `nPatches`.

#' @param options named values that override defaults

State indices

Retrieve stored indices with the shared ramp.xds::get_MY_ix(xds_obj, s = 1); the species index defaults to 1. Do not implement a module-specific getter. It returns the ix field directly: a named list of variable indices, an empty list if stored, or NULL if absent. Getter documentation uses “Get variable indices (MY)”, describes returning stored indices for the selected vector species, puts storage in @note, and links to setup_MY_ix.

setup_MY_ix.newMYname assigns a contiguous index range to each state variable. The example follows the SI implementation; add or remove index ranges to match the model and store them in the named list at xds_obj$MY_obj[[s]]$ix.

Use the title and description below, documenting actual allocation order and block lengths, including any auxiliary or matrix/cohort blocks. Put storage and the updated maximum in @note. Return the model object, not the index list; flag legacy storage or return errors separately.

#' @title Set up variable indices for `newMYname` (**MY**)
#' @description Assign consecutive variable indices for the `newMYname` module,
#' starting after `xds_obj$max_ix`, and update the maximum index.
#' Allocate blocks in the order `M_ix`, `Y_ix`.
#' Each block has length `nPatches`.
#' @note Indices are stored at `xds_obj$MY_obj[[s]]$ix`.
#' The maximum index is stored at `xds_obj$max_ix`.
#' @inheritParams ramp.xds::setup_MY_ix
#' @return an **`xds`** model object
#' @importFrom utils tail
#' @export
setup_MY_ix.newMYname <- function(xds_obj, s) {
  with(xds_obj, {
    M_ix <- seq(from = max_ix + 1, length.out = nPatches)
    max_ix <- tail(M_ix, 1)

    Y_ix <- seq(from = max_ix + 1, length.out = nPatches)
    max_ix <- tail(Y_ix, 1)

    xds_obj$max_ix <- max_ix
    xds_obj$MY_obj[[s]]$ix <- list(M_ix = M_ix, Y_ix = Y_ix)
    xds_obj
  })
}

It neither parses outputs nor modifies the model object. Link its documentation to parse_MY_orbits and xds_solve.

parse_MY_orbits.newMYname <- function(outputs, xds_obj, s) {
  with(xds_obj$MY_obj[[s]]$ix, {
    M <- outputs[, M_ix]
    Y <- outputs[, Y_ix]
    list(M = M, Y = Y)
  })
}

Plotting

Use the shared ramp.xds::xds_plot_M, ramp.xds::xds_plot_Y, and ramp.xds::xds_plot_Z helpers when parsed outputs include adult, infected, and infective mosquito densities. The fraction helpers ramp.xds::xds_plot_Y_fracs and ramp.xds::xds_plot_Z_fracs require saved y = Y/M and z = Z/M; they do not compute fractions. These ordinary functions read the selected species’ saved orbits through ramp.xds::get_MY_orbits and draw one line per patch. Do not implement module-specific methods for them.

Plot helpers create a new plot unless add = TRUE; corresponding ramp.xds::xds_lines_* helpers add lines to an existing plot. Pass one color or line type for all patches, or vectors with one value per patch. The helpers return invisible(NULL). Use titles such as “Plot infected mosquito density (MY)” and “Add lines for the infective mosquito fraction (MY)”. Keep required fields and overlay behavior in @note, and link plot and line helpers reciprocally. Module-specific visualization remains optional.

Reusable model code

ramp.xds has a modular design that allows published models to serve as dynamical components in new models for malaria and other mosquito-transmitted pathogens, including ordinary and delay differential equation models and stochastic or deterministic discrete-time models.

The mathematics supporting this framework are described in Spatial Dynamics of Malaria Transmission. 1
